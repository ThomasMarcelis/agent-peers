# Reference

## CLI

| Command | Output |
| --- | --- |
| `agent-peers list [--all-names]` | Sessions with compact observed status and exact messaging targets, then running [claimed names](#names) plus a count of non-running reservations. `--all-names` expands those reservations. A separate section shows [recently exited Codex sidecars](#codex-runtime-status) |
| `agent-peers list --json` | `{ "peers": [...], "names": [...], "recentlyExited": [...] }`; no status text mixed into stdout. Each peer row carries its [`generation`](#delivery-protocol) and `claims`, the names it holds. opencode rows also carry `threadId` (the root opencode session id). Records whose process is gone, or whose PID now belongs to another process, are absent from `peers`; status-aware recent exits are separate (below). Each peer socket gets a short (200 ms) connect probe with no data sent; a refusing socket is shown as `stale` and has `reachable: false`. Codex listings never delete records; a later sidecar bind can reap dead records older than the recent-exit window. An opencode record is removed when its bridge unbinds. `--no-probe` skips the probe and omits `reachable`. `names` lists every claimed name, running or not (see [names](#names)) |
| `agent-peers whoami [--json]` | The calling session's name and `uds:` address (and `generation` and `claims` in JSON), found by walking process ancestry to a PID with a Claude session record (or a Codex inbox record). Exits 1 outside a session; never guesses by working directory. A process detached from the session (`setsid`, a daemonized launcher, a systemd unit) has no such ancestor: run `whoami` before detaching and pass the address on. opencode has no CLI identity and is not identified here; use its tools |
| `agent-peers claim <name> [--json]` | Claims `claude:<scope>/<claim>` (or `<scope>/<claim>`) for the calling Claude session, found by ancestry like `whoami` but Claude only. The walk stops at the first agent process without a Claude session record (a `claude`, `codex`, `hermes` or `opencode` process, or Node or Python running one), so a worker an agent started never claims for the session above it. Other agents run from a Claude session's shell, such as gemini, aider or goose, are not recognised: a claim they run is made for that Claude session. Prints the [claim result](#claim-and-release-results). Exits 1 when refused, including `no-session` outside a Claude session or inside such a worker, and 2 for a name outside the grammar |
| `agent-peers release <name> [--json]` | Removes a name this session holds, or a `claude:` name whose holder is not running (also outside a session). Codex, Hermes and opencode names are `scope-denied`: their own sessions release them. Exits 1 when refused |
| `agent-peers resolve <target> [--json]` | Prints exactly one `uds:` line for a claimed name, an exact peer name or an address: the holder's inbox in the calling Claude session's socket directory when it has one, else its primary inbox. opencode names are ordinary registered inboxes. JSON: `{status: "resolved", reason: null, name, kind, address, generation, text}`, or `{status: "failed", reason, text}`. For a name a Hermes conversation holds, it also tells that conversation which Claude session is about to send, and waits up to a second for its answer ([names](#names-and-the-reply-target-allowlist)). Exits 1 for `not-found`, `not-running`, `ambiguous` or `inbox-unavailable`, and when that conversation will not admit the session (`not-holder`, `unknown-sender`, `inbox-closed`); 2 for invalid usage or grammar |
| `agent-peers send <target> --stdin [--label <label>] [--json]` | Sends one one-way notice, read from stdin, to a claimed name, an exact peer name or a `uds:` address, for scripts and jobs that are not agent sessions ([experimental](stability.md#experimental)). Each call is its own sender: a temporary inbox `script-<id>.sock` beside the target's inbox, open only for the [receipt window](#delivery-protocol) and removed on exit, including on SIGINT, SIGTERM and SIGHUP. It never sends as a session and needs none in its ancestry, so a detached job can use it. The envelope's `from-name` is `script:<label>` (label `[a-z0-9][a-z0-9_-]{0,55}`, default `script`), which is attribution, not authentication. A footer tells the recipient that replying to its address does nothing; a reply that arrives during the window gets `dropped`/`inbox-closed`. Name the peer to talk to in the body (for example `Discussion: hermes:gaming/relay`); the command never reads it. Prints the [send result](#send_peer-result) plus `outcome` and `reply: false`; see [script sends](#script-sends) for outcomes and exit codes |
| `agent-peers doctor [--json]` | Runtime, dependency, and local path checks, plus one read-only request to the Codex app-server to confirm it answers. For opencode it reports the binary/version, whether the global config's `plugins` lists `agent-peers`, the live opencode record count, and the installed plugin package version next to the CLI version (a warning on skew, `unknown` when it cannot resolve the package). It never starts a server, reads a password, or writes configuration; a missing opencode is a warning. |
| `agent-peers logs [--json]` | Read-only summary of retained local diagnostic events |
| `agent-peers --version` | Package version |
| `agent-peers --help` | Usage |
| `codex-peer` | Codex MCP server over stdio |
| `agent-peers hermes-bridge` | Plugin-managed JSON-lines subprocess |

Exit codes: `0` success, `1` runtime/diagnostic failure, `2` invalid CLI usage. Missing agent state is a diagnostic warning because running only one integration is valid, and so is a Codex app-server that does not answer, such as a stale socket left after a reboot. An answering app-server does not prove compatibility or model readiness.

## Tools

`list_peers({all_names?: boolean})` in Codex and opencode defaults to showing only running names in text, plus a count of non-running reservations; `all_names: true` expands them. Structured `names` always contains every reservation. Codex's structured result contains `peers`, each with its name, kind, working directory, available [runtime status](#codex-runtime-status), native/bridge route, `generation` and `claims`; `self`, the caller: `{name, kind, address, addresses, generation, threadId, subagent, claims}`; `names`; and `recentlyExited`. A subagent's address and claims are its root's, and `self` is never in `peers`. The text opens with `You are <name>.` Native reachability is caller-relative: another root is bridge-only even on the same daemon. Discovery does not load historical Codex threads. Hermes's JSON-text result is `{peers, names, recentlyExited}`, with every reservation and each peer row's name, kind, working directory, status, address, `generation` and `claims`; a Hermes conversation appears only through a name it claimed. opencode's result has the same `{peers, self, names, recentlyExited}` shape as Codex; `self.threadId` is its root session id, `self.sessionID` is the caller's own session id (the child's for a subagent), and `self.subagent` is true for a child session.

`send_peer({to, message, in_reply_to?})` sends one message:

- `to` is an inbox address (`uds:…`), a [claimed name](#names), an exact peer name, or an exact name without its kind prefix when only one kind has it. Nothing else matches: no fragments, most-recent guesses, defaults or broadcasts. An unknown name fails `not-found` and lists up to five exact names that contain it.
- `in_reply_to` is the `id` of the message being answered (`[A-Za-z0-9_-]{1,128}`); an empty string means none. It appears on the recipient's frame and is echoed in the result. It is advisory and never checked against received ids.

`claim_name({name})` claims a [stable name](#names) for the calling session, and `release_name({name})` removes one. Codex takes `codex:<scope>/<claim>` or `<scope>/<claim>`; opencode takes `opencode:<scope>/<claim>` or `<scope>/<claim>`; a subagent of either gets `no-session`, because it sends under its root. Codex releases only `codex:` names and opencode only `opencode:` names: its own, or one whose holder is not running. Hermes takes `<claim>`, `<scope>/<claim>` or `hermes:<scope>/<claim>`, where the scope must be the conversation's own profile id, for claims and releases alike; it needs a live conversation route, as `send_peer` does, and otherwise gets `no-session`. They return the [claim result](#claim-and-release-results); Codex and opencode set `isError` when it is `refused`, and Hermes adds `error`.

Hermes handlers return JSON text, as its dispatcher requires; Codex returns MCP text content plus `structuredContent`.

opencode exposes the same four tools with the same names and input schemas (the release's copy is `src/peer-tool-definitions.json`, compared with Codex's `tools/list` in the tests). It declares **no output schemas**: each result has two text content blocks, the human text and `JSON.stringify(structuredContent)`, plus `metadata: {structuredContent, isError}` and no `output`. opencode's model sees only `content`, so the second block carries the same structured object a Codex model reads. opencode identity is tool-only: `list_peers.self`, `claim_name`, `release_name` and `send_peer` know the caller; `agent-peers whoami` and `agent-peers claim` do not, and `OPENCODE_SESSION_ID` is not read as an agent-peers identity. An opencode child (subagent) session sends under its root and gets `no-session` from `claim_name`/`release_name`, exactly as a Codex subagent does.

### send_peer result

```json
{ "status": "accepted", "reason": null, "message_id": "…", "in_reply_to": null,
  "to": "uds:…", "name": "codex:api-ab12", "generation": "3f9a0c1b2d4e5f60", "from": "uds:…" }
```

`to`, `name` and `generation` describe the target. `from` is the reply address the recipient sees. Fields not known yet are `null`. Codex returns this object as `structuredContent`, with prose in the text content. opencode returns the same object in its second text block and `metadata.structuredContent`. Hermes returns it with `text` added, plus `error` (the same text) exactly when the status is an error. Codex and opencode set `isError` by the same rule.

| `status` | Meaning | Error |
| --- | --- | --- |
| `accepted` | The recipient's host took the input (agent-peers 1.0 recipients) | no |
| `queued` | The recipient's inbox admitted it; its host had not answered when the window closed | no |
| `held` | A Claude recipient holds it for its user's approval; a reply may still come if approved | no |
| `delivered` | A held message was released | no |
| `unconfirmed` | Written, but no receipt arrived. This is the normal success case for Claude recipients, which report only exceptions | no |
| `dropped` | The recipient's inbox or host did not deliver it | yes |
| `denied`, `expired`, `refused` | A Claude recipient's user declined it, it was never approved, or the recipient refuses peer input | yes |
| `failed` | Nothing deliverable was written | yes |

An error status means the message was definitely not delivered. Nothing is retried automatically, because a timed-out write or a lost bridge may already have delivered. No status proves that a model read the message.

`reason` is a stable kebab-case code, or `null`. Clients must tolerate new codes.

- `failed`: `invalid-request`, `not-found`, `ambiguous`, `invalid-address`, `self-send`, `native-route-required`, `not-running`, `too-large`, `write-timeout`, `write-failed`, `inbox-unavailable`, `too-many-pending`, `unsupported-host`, `conversation-closed`, `bridge-unavailable`.
- `dropped`: Claude's `rate-limited`, `duplicate`, `queue-full`, `hop-loop`, `hop-runaway`; agent-peers' `too-large`, `host-rejected`, `inbox-closed`, `not-a-reply-target`; or `other`.
- `unconfirmed`: `no-receipt`, `bridge-lost`.

For a claimed name, `name` is the claimed name and `generation` its current holder's. When the holder is a different session than at this sender's previous send to that name, the send still goes through and the text says so.

### Script sends

`agent-peers send` makes one send attempt and never retries. That does not make processing at most once: a message whose outcome is `sent` or `uncertain` may already be in the recipient's context, so put an id in the body that lets the recipient recognize a repeat. `outcome` says what a script may do next:

| `outcome` | Exit | Results | Meaning |
| --- | --- | --- | --- |
| `sent` | 0 | `accepted`, `queued`, `unconfirmed`, `held`, `delivered` | Written. `unconfirmed` is the normal success for a Claude recipient; `held` waits for its user's approval |
| `retry` | 3 | `dropped` with `rate-limited` or `queue-full` | Definitely not delivered; a later attempt may succeed |
| `unreachable` | 4 | `failed` with `not-found`, `not-running` or `inbox-unavailable`; `dropped` with `inbox-closed` | No running holder or inbox took it; nothing was delivered |
| `uncertain` | 5 | `failed` with `write-timeout` or `write-failed` | The line may have arrived. Sending it again can duplicate it |
| `rejected` | 1 | everything else, such as `too-large`, `denied`, `refused` or `dropped`/`not-a-reply-target` | Not delivered, and repeating it unchanged will not help |

Invalid usage, including an empty body, exits 2 with `invalid-request`. A negative receipt that arrives after the window closes reaches nobody, because the temporary inbox is gone. Name resolution, pins and admission are those of `send_peer`: a Hermes holder admits the script because the line carries the name it holds (`agent_peers.to_name`), and a Hermes conversation's inbox found by address drops it with `not-a-reply-target`.

### Claim and release results

```json
{ "status": "taken-over", "reason": null, "name": "hermes:gaming/relay", "kind": "hermes", "generation": "…", "address": "uds:…",
  "previous": { "holder": "hermes:gaming:ab12cd34", "generation": "…", "running": false }, "text": "…" }
```

`agent-peers claim` and `release`, and the `claim_name` and `release_name` tools, return this object. `generation` and `address` describe the name's holder after the call: the claimant after a successful claim, `null` after a release or a refusal. `previous` describes the record that was there (its holder's automatic name, its generation and whether that holder was running), or is `null`.

| `status` | Meaning |
| --- | --- |
| `claimed` | The name was free; this session holds it now |
| `refreshed` | This session, or an earlier process of the same claimant (a restarted Codex MCP server, a Hermes conversation after a gateway restart), already held it; it now names this process |
| `taken-over` | Another claimant held it but is not running; this session holds it now, and `previous` names the old holder |
| `released` | The record was removed |
| `refused` | Nothing changed; `reason` says why |

Refusal reasons: `invalid-request` (outside the grammar), `name-held` (a running holder keeps its name; only it can release it), `not-holder` (a release of a running holder's name), `not-found` (a release of a name nobody claimed), `scope-denied` (a claim or release of another kind's name, or for Hermes another profile's), `no-session` (no calling session: outside Claude for the CLI, or inside an agent process without a Claude session record; a Codex subagent or replaced MCP process; a Hermes conversation without a route), `too-many-names` (8 per claimant, or 1024 names on this machine for a new one; the text lists the names the caller may release itself, or tells it to ask its user), `conflict` (the record changed while this call ran; try again), `inbox-unavailable` (a Hermes conversation could not open its inboxes), `unsupported-host` (a Claude Code build whose session registry records no process start time; see [claiming](#names)) and `bridge-unavailable`. A record written by a newer agent-peers (a higher `v`) is refused with `name-held` or `not-holder`, even to its holder.

## Codex runtime status

**Experimental, additive fields.** A bound Codex sidecar records runtime observations in its existing registry file. This works on a private app-server and for TUI roots served by the configured app-server. CLI discovery reads that registry without contacting any app-server; Codex's existing native discovery can additionally observe loaded members of the caller's own tree. Native children without a sidecar have only the status/timing evidence returned by that discovery, usually no last-turn outcome. Older sidecars and inaccessible runtime evidence add no fields. An app-server disconnection or failed metadata read reports `unknown`, never an inferred busy, idle or dead state.

| Peer field | Evidence and meaning |
| --- | --- |
| `status` | Runtime `active`, `idle`, `notLoaded`, `systemError`, or observer `unknown`. Text renders `active` as `busy`. A failed turn does **not** imply idle; Codex may report `systemError` |
| `statusObservedAt`, `statusSource` | Unix milliseconds when the sidecar observed the value; source `thread/read`, `thread/status/changed`, or `thread/loaded/list` (the thread is absent from the loaded set). `app-server-unavailable` explicitly records loss of observation, not a runtime state |
| `lastActivity` | `{turnId, at, observedAt, source, event, timeSource}` for the latest proven turn start/completion. `at` and `observedAt` are Unix milliseconds; `event` is `started` or `completed`; `source` is `turn/started`, `turn/completed` or `thread/turns/list`. `timeSource: "runtime"` uses the runtime's seconds timestamp converted to milliseconds. A notification lacking it uses receipt time with `timeSource: "observed"`. Historical summaries without timestamps cannot prove activity time and leave it absent |
| `lastTurn` | `{id, status, observedAt, source, completedAt?, errorClass?}` for the most recent observed terminal turn (`completed`, `failed`, `interrupted`), retained while another turn runs. `completedAt` is runtime time in milliseconds and stays absent when unknown. Text then says `observed HH:MMZ` instead of claiming completion time |
| `lastTurn.errorClass` | Failed turns only: an allowlisted runtime `codexErrorInfo` variant converted to snake case (for example `server_overloaded`), or a structured HTTP code (`http_409`). Free-form error messages, additional details, prompts and item contents are never stored or displayed |

Status-change notifications update observations immediately; background metadata reads reconcile every 15 seconds. Observer connections do not necessarily receive turn notifications, so the sidecar requests at most the latest **two** turns using `thread/turns/list` with `itemsView: "notLoaded"`. These reads use a separate app-server connection with one-second connection/handshake/RPC timeouts, run outside the inbox delivery chain, check the loaded set before thread reads, and never answer approvals or tools. Ephemeral threads reject the turn-summary API; their outcomes are unavailable unless turn notifications arrive. Unknown/unsupported turn APIs leave outcomes absent. Silence alone changes no runtime state. Text such as `busy · seen 3m ago` states observation age, **not** three minutes continuously busy. Turn times use UTC (`Z`).

`recentlyExited` is a separate array in CLI and tool JSON, excluded from `peers`, name resolution and messaging routes. It contains status-aware Codex sidecars whose PID is gone or whose recorded process-start token no longer matches, **and** which wrote a status record within the last 60 minutes. This proves a recent sidecar exit, not whether its Codex thread or launcher still runs. Entries carry `{name, kind, threadId, cwd, ...statusFields, lastSeenAt, exitObservedAt, exitBasis: "pid-gone-or-reused", inboxClosedAt?}` and no inbox address. `lastSeenAt` is the registry write time; `exitObservedAt` is this listing's detection time, not the exact exit time. Optional `inboxClosedAt` records graceful sidecar inbox closure, also not process exit. Text says `exit observed HH:MMZ · last turn failed HH:MMZ (http_409)` and uses only the last recorded outcome. Normal sidecar shutdown retains the status record; dead records older than the window can be cleaned up by a later sidecar bind. Listings remain read-only. Pre-upgrade exits and old records without status/write timestamps cannot appear here.

## Delivery protocol

**Receipts.** agent-peers inboxes answer in Claude Code's receipt format, `{type:"control", action:"peer_message_status", orig_msg_id, status, …}`. Every sender, including Claude Code and agent-peers 0.x, gets `dropped` with a `drop_reason`. Only senders that opt in also get `queued` when the inbox admits a message and `accepted` when the host takes it. The sender waits up to 1.5 s after its write completes and counts a receipt only if its `from` is the inbox it wrote to. That check is not authentication: like names and addresses, receipts are unauthenticated between processes of the same user ([security](../SECURITY.md)). A repeated `msg_id` from the same sender is discarded with no receipt, so the first copy's outcome stands. Identical bodies with different ids are both delivered.

**Hermes reply inboxes.** A Hermes conversation's inboxes accept messages only from its reply targets: the addresses that conversation has sent to, in any of its socket directories, and the senders that addressed it by a name it holds (see [names and the reply-target allowlist](#names-and-the-reply-target-allowlist)). Both last until it closes, up to the latest 256 peers it sent to and, kept apart with rate limits of their own, the latest 64 senders by name. Any other sender gets `dropped`/`not-a-reply-target`. An unclaimed Hermes conversation is never listed, so finding one of its inboxes in the socket directory and writing to it is unsupported; ask the Hermes conversation to send first, or to claim a name.

**Late outcomes.** A negative or `held` receipt that arrives after the result was returned reaches a Codex session as one short notice appended to its history, which never starts a turn. Hermes logs it only. Late positive receipts are silent.

**Line extension.** agent-peers adds `agent_peers: {v: 1, receipts: ["queued", "accepted"], generation, in_reply_to, to_name}` to each message line it sends, and `agent_peers: {v: 1}` to each receipt. `to_name` is present only when `to` was a claimed name, and is that name; a Codex or Hermes recipient that does not hold that name when the line arrives drops it with `not-a-reply-target`. Claude Code and agent-peers 0.x ignore it, and the `<cross-session-message>` envelope is unchanged. Readers ignore unknown fields and accept higher versions. Claude recipients cannot see `in_reply_to`, so a reply to a Claude session ends with `(In reply to <id>.)` instead.

**Generation.** `generation` is an opaque 16-hex-digit string that changes when a different process takes over a PID or an inbox path. Claude sessions keep theirs across `/clear` and `/resume`. A Codex session gets a new one when its MCP server restarts. A record counts as running only if its PID is alive and that process started when the record says. Each Codex session (with its subagents) and each Hermes conversation remembers the generation it saw behind every name and address, from its own listings, incoming messages and first send; one never vouches for another. If a later send finds a different process there, it fails `not-running` instead of reaching the wrong session. Listing again refreshes this.

**Automatic names.** Automatic names are `<kind>:<label>`, where the label uses letters, digits and `_ . : -`. Other characters in Claude session names and Codex labels become `-`, so an automatic name never contains `/` and can never collide with a [claimed name](#names). `@ * ? ,` and whitespace fail `invalid-request` and will never mean patterns or broadcast.

**Codex app-server requests.** The app-server sends its requests (approvals, user input, dynamic tool calls, token refresh, attestation) to every connected client, and the first answer wins. agent-peers never answers one, so each waits for the client that owns it, as it would without agent-peers. With diagnostics enabled, each is logged as `server_request` with its method.

## Names

Claimed names are [experimental](stability.md#experimental) in 1.x: their commands, fields and storage may change in a minor release.

A session or conversation can claim a stable name, so that peers reach whoever holds the role now instead of an address that dies with a restart. A name is claimed explicitly, scoped, resolved at send time, and never falls back to anyone else.

**Grammar.** `<kind>:<scope>/<claim>` with exactly one `/`: kind `claude`, `codex`, `hermes` or `opencode`; scope `[a-z0-9][a-z0-9_-]{0,63}`; claim `[a-z0-9][a-z0-9_.-]{0,63}`. Matching is exact and case-sensitive; anything else, such as an uppercase letter, a second `/` or a `:` in the scope, is `invalid-request`. For Hermes the scope is the conversation's profile id, enforced by the plugin and by its bridge (`hermes:gaming/relay` in profile `gaming`); for Claude, Codex and opencode it is a project namespace the owner chooses, which organizes names and is not a security boundary. The kind-elided form `<scope>/<claim>` resolves only when exactly one kind has a record for it, running or not; otherwise it fails `ambiguous` and lists the full names. Claim commands fill in the caller's own kind.

**Claiming.** Claude runs `agent-peers claim <name>` from the session (its Bash tool); Codex, Hermes and opencode call `claim_name`. A session can claim only names of its own kind, at most 8. Who holds a name:

| Kind | Claimant (owner) | Holder is running when |
| --- | --- | --- |
| Claude | the Claude process (PID and start time) | that process still runs: its PID is alive with the start time the claim recorded |
| Codex | the root thread | the MCP server process that claimed it still runs, with the start time the claim recorded, and still serves the thread: `codex-<threadId>.json` names that process |
| Hermes | the profile and Hermes conversation id | the bridge process still runs, with the start time the claim recorded, and at least one inbox the claim recorded still exists |
| opencode | the root opencode session | the opencode bridge process that claimed it still runs, with the start time the claim recorded, and still serves the session: `opencode-<sessionID>.json` names that process |

Only this evidence in the record decides whether a holder stopped. A holder that runs but that this process cannot see, because it uses another `CLAUDE_CONFIG_DIR` or a socket directory this process does not know, or because Claude is rewriting its session file, is still running: listings show it running with `address: null`, a send or `resolve` to it fails `inbox-unavailable`, and nobody else can take it over or release it. The registry views only choose the address a send goes to. A holder is always the user's own process, so a PID that now belongs to another user's process counts as stopped.

A Claude claim needs the session's start time in Claude's session registry, which current Claude Code records. Without it the claimant would be a PID alone, and a later session that reuses the PID and socket path could inherit the name, so such a claim is refused with `unsupported-host`; update Claude Code to claim names. A claim recorded without a start time (by 1.0.0-rc.2) counts as not running.

A Codex root's names stay held while the MCP server process that claimed them runs and still serves that thread. Codex TUI `/new` and resume keep one MCP process across threads, so a root left behind by `/new` keeps its names, and still receives messages sent to them, while that process serves it; once the process stops serving it (its `codex-<threadId>.json` is removed), the names count as not running and can be taken over.

An opencode root's names stay held while its bridge child runs and `opencode-<sessionID>.json` still names that bridge. A bridge restart is a new generation of the same owner, so the root's next bind refreshes its names; after a server or bridge exit they read `not-running` until that bind, exactly as for Hermes.

A claim on a free name is `claimed`. The same claimant refreshes its own name without any flag, also from a new process: a Codex MCP server takes back its thread's names when it binds, and a Hermes conversation takes back its names on its next agent-peers call after a gateway restart (`list_peers`, `send_peer`, `claim_name` or `release_name`). A name whose holder is not running is `taken-over`, and the result names the previous holder. A running holder is always refused with `name-held`; only it can release the name. A Hermes conversation's names also follow it through compression, which changes its conversation id while its route lives, and the inboxes it opens later; see [the Hermes limitation](hermes.md#stable-names) when the gateway restarts right after a compression.

**Releasing.** A session releases a name it holds. Once the holder is not running, a session of the same kind may release it too, and for Hermes only one of the same profile; `agent-peers release` outside any session releases dead `claude:` names. A dead name of another kind or profile is `scope-denied`, because its own claimant may be about to take it back after a restart. An opencode session releases only `opencode:` names; a dead `opencode:` name can be taken over or released by another opencode session.

**Resolution.** A sender resolves a claimed name each time it sends: `send_peer({to: name})` for Codex and Hermes, and `agent-peers resolve <name>` followed by `SendMessage` to the printed address for Claude. No record fails `not-found`; a holder that is not running fails `not-running`, naming the holder and when it claimed the name; a running holder this sender cannot see fails `inbox-unavailable`. Nothing is ever sent to another session instead. A claimed name follows its holder, so a different generation behind it is not a pin failure. Between `resolve` and `SendMessage` the holder can change; a dead socket then fails at Claude.

**Listing.** `list --json` and `list_peers` return `names`: `{name, kind, running, address, addresses, generation, holder, claimedAt}`. Dead names stay listed with `running: false`, `address: null` and `holder: null` until a new claim or a `release` replaces them; they do not expire. A running holder this process cannot see has `running: true` and `address: null`. `holder` is the running holder's automatic name, `addresses` its current inboxes (`address` the one in the calling Claude session's socket directory for the CLI, else the first), and `claimedAt` the time of the last claim in milliseconds. Peer rows carry `claims`, the names they hold.

**Frames.** A Codex, Hermes or opencode recipient adds `reply_name="<name>"` to `<peer_message …>` only when its own lookup finds a running claim held at the sender's address. A name a sender asserts is never shown. The first message from a Codex, Hermes or opencode session to a Claude session adds `(Stable name: <name>.)` when the sender holds one.

**Storage.** One file per name, `$AGENT_PEERS_HOME/names/n-<sha256(name)[:32]>.json`, mode `0600`, in a `0700` directory owned by the user, with the registry's rules: never read through a symlink, and dropped when foreign, group- or world-writable, over 64 KiB, or not matching its file name and kind. The record is `{v: 1, name, kind, owner, generation, claimedAt, holder: {pid, procStart, autoName, socket (Claude), threadId (Codex), addresses}}`; `owner` and `generation` are hashes, never raw conversation or route ids. A new name is published with a hard link, which fails if it exists; a running holder refreshing its own record replaces it in one rename; any other replacement or removal renames the file aside and checks it is still the file that was read, else puts it back and reports `conflict`. A file that cannot be read at that moment is refused with `conflict`, and a record with a higher `v` than this version writes with `name-held` (claim) or `not-holder` (release), even when this version can read it; neither is ever replaced or removed, and `resolve` still uses a higher-`v` record that validates. A new name is refused with `too-many-names` once the directory holds 1024 names, so every listing and re-claim reads all of them; refreshes and takeovers replace a record and still work. There is no lock or daemon. Exit never removes a record. If a running holder will never release a name (for example a process that is stuck but must keep running), the user can free it by deleting that name's `$AGENT_PEERS_HOME/names/n-*.json` file (the file is `n-` plus the first 32 hex digits of the SHA-256 of the full name, which `printf %s 'codex:team/lead' | sha256sum | cut -c1-32` prints for `codex:team/lead`); agent-peers itself never does this. A claim or release that died midway can leave a `.reap-<uuid>.json` (a record a claim moved aside), `.rel-<uuid>.json` (one a release moved aside) or `.t-<uuid>.json` (one never published) file. The next claim or release handles those that are this user's regular files and were last changed more than a minute ago: a `.reap-` record whose name file is gone is put back, because it may be a running holder's record that was being swapped, and the rest are removed, apart from a `.reap-` record with a higher `v`.

**Races.** Concurrent claims of one name end with at most one record, and its holder is the only one any reader resolves. In the worst case, three claims of the same name within microseconds (two takeovers and a new claim), a claim that was reported successful can be lost: senders then resolve the record that won, or get `not-found`, until the loser claims again. There are never two holders. A line sent by name carries the name it was resolved for (`agent_peers.to_name`), and a Codex, Hermes or opencode recipient that does not hold that name when the line arrives, because it lost such a race or released the name after the sender resolved it, drops the line with `not-a-reply-target`. So a message sent by name to a Codex, Hermes or opencode holder reaches only the session that holds the name. A Claude recipient cannot check the name: a Claude sender resolves just before `SendMessage`, and between the two the holder can change, as with any `uds:` address.

### Names and the reply-target allowlist

A Hermes conversation's inboxes accept only its reply targets (#28). A claimed name opts that conversation into unsolicited messages addressed by its name, and only by its name:

- A Codex or Hermes `send_peer` to a claimed name marks the line with `agent_peers.to_name`. The receiving conversation admits the sender when it holds that name and a socket of this user exists at the sender's address, and the sender becomes one of its reply targets. A conversation remembers the latest 64 senders admitted by name, with rate limits of their own, apart from the up to 256 peers it wrote to, so senders by name never push out a peer it is talking to or use up its limits; a forgotten sender is admitted again by its next line that carries the name.
- Claude's `SendMessage` cannot mark a line, so `agent-peers resolve <name>`, run by the sending Claude session, tells the holding conversation which session resolved its name: a `{type: "control", action: "name_resolved", msg_id, from, name, agent_peers: {v: 1}}` line to the inbox it printed, whose `from` is the calling session's address. The conversation admits that address if it is a live Claude session it can see and the name is one it holds, and answers on the same connection: `{type: "control", action: "name_resolved_status", from, orig_msg_id, status: "admitted"}`, or `status: "dropped"` with a `drop_reason` of `not-holder` (it no longer holds the name), `unknown-sender` (it sees no live Claude session at that address, for example because the two use different `CLAUDE_CONFIG_DIR`s) or `inbox-closed`. `resolve` waits up to a second for the answer and fails with that reason when it is `dropped`; a bridge older than this answers nothing, which `resolve` takes as admitted. A bridge skips answers on a connection that already has 64 KiB of them unread, so a sender that writes many `name_resolved` lines without reading cannot grow its memory; `resolve` writes one line and reads its answer.
- The admission lasts for the conversation, not for the name: a sender admitted by name stays a reply target until the conversation closes (or until 64 later senders by name push it out), even if the conversation releases the name.
- A sender that writes to the same inbox without its name, for example after finding it in the socket directory, still gets `dropped`/`not-a-reply-target`, as does any line marked with a name this conversation does not hold, even from a reply target.

Like every agent-peers name and address, this is not authentication: any process of the same user can write the same line ([security](../SECURITY.md)). It stops misrouting, not a malicious local process.

## Environment

| Variable | Purpose |
| --- | --- |
| `CLAUDE_CONFIG_DIR` | Claude configuration directory used to locate session registry metadata |
| `CODEX_HOME` | Codex home used to locate its shared daemon |
| `AGENT_PEERS_HOME` | agent-peers registry directory |
| `AGENT_PEERS_CODEX_APP_SERVER` | Absolute path to the Unix socket of the app-server hosting this Codex thread, such as a [private app-server](compatibility.md#headless-codex-on-a-private-app-server); defaults to Codex's shared daemon |
| `AGENT_PEERS_NAME` | Codex only: replaces the folder or title in the session's peer name, which keeps its `-<id>` suffix. Codex passes MCP servers only a few variables, so set it in `[mcp_servers.agent-peers.env]` |
| `AGENT_PEERS_DEBUG` | Set to `1` to record structured local diagnostics; `0` disables recording, including an explicit log file |
| `AGENT_PEERS_LOG` | Optional absolute private JSONL log file; enables diagnostics unless `AGENT_PEERS_DEBUG=0` |
| `AGENT_PEERS_NODE` | opencode plugin only: a Node.js 22+ executable for the bridge. `bridge_command` takes precedence and skips this lookup |

Defaults use the current OS user's standard agent directories. Every override should be absolute. Package-owned socket and registry state must have private ownership/permissions. The transport is local and same-user; it is not a network service.

## Local diagnostic logging

Logging is opt-in. Set `AGENT_PEERS_DEBUG=1` in the environment inherited by the Codex MCP server or Hermes bridge, then restart that integration through its normal lifecycle. It creates a `logs` directory under the agent-peers registry directory on the first event. `agent-peers doctor --json` reports the current shell's logging configuration without creating files or checking delivery. A running integration may have inherited a different environment.

Events are newline-delimited JSON with timestamps, process IDs, component/event names, operation IDs, delivery stages, byte counts, durations and bounded error categories. Thread, target and session identities are hashed for local correlation. These pseudonyms are not anonymization: known candidate identities can be hashed and matched. Message bodies, thread titles, peer names, filesystem paths, credentials, raw error text, request parameters and model responses are excluded. Standard output remains reserved for CLI or protocol results.

The default directory has mode `0700` and process-specific files have mode `0600`. Files rotate at 1 MiB; retention runs when writing and keeps at most 32 files / 16 MiB and seven days of recently modified files. Concurrent processes use separate files. Unrelated files are never retention candidates. Symlinked path components, shared writable ancestors, non-private destinations, hard links and non-regular log files are rejected. A logging failure emits at most one generic warning per process to standard error and never stops messaging.

`AGENT_PEERS_LOG` preserves an explicit append-only file destination, with the same private-directory and file checks. It stops accepting events at a 1 MiB size check instead of renaming or truncating a destination another process might use; simultaneous writers at the boundary can append one additional bounded record each. It has no age-based expiration. Prefer the default directory for sustained use. Old plain-text logs may contain identifying information from older releases and are not converted or deleted automatically.

Run `agent-peers logs --json` with the same environment to inspect retained events, outcomes, failure reasons, terminal tool calls by method, delivery stages and incomplete operations. The command reads existing files even when recording is disabled, tolerates malformed/legacy lines, applies read limits, and never creates or prunes state. It can show sends and discovery activity observed by agent-peers after logging was enabled. It cannot reconstruct unlogged history, native collaboration calls, arbitrary shell failures or calls made through another integration such as `codex_tui`. It does not collect token usage, billing, model reads or replies. An incomplete operation may still be running, may have been interrupted, or may have lost its earlier/later events to retention.

An **inbox write** means the local socket write completed. A **receipt** records the recipient's reported handling. **Emitted to host** means the Hermes bridge sent an event to its host. **App-server input accepted** means the daemon acknowledged the input request. None proves that a model read the message or produced a reply; counts at these different stages must not be added together as total messages.

## Hermes subprocess protocol

Internal: the plugin and its bridge ship together in one package version, so this protocol is not covered by semantic versioning ([stability](stability.md)) and may change in any release.

Requests are newline-delimited JSON objects `{id, method, params}`. Responses are `{id, result}` or `{id, error}`. The bridge handles requests concurrently, up to 128 awaiting a response, keeping order per conversation, so responses can arrive out of order. Methods:

- `list_peers`: optional `session`, with `owner` (the Hermes conversation id) and `identity` (its `hermes:` automatic name). The listing pins generations for that conversation only; without it, it pins nothing. With an owner it first takes back the conversation's names, once per route, owner and set of inboxes; a name whose refresh was refused is tried again at most once a minute.
- `send_peer`: `session`, `owner`, `name` (the `hermes:` identity), `to`, `message`, optional `in_reply_to`. The result is the [send_peer result](#send_peer-result) plus `text`.
- `claim_name`, `release_name`: `session`, `owner`, `identity`, `name` (a full claimed name). The result is the [claim result](#claim-and-release-results).
- `close_session`: `session`.
- `shutdown`: finish in-flight requests, close owned state and exit.

The plugin starts the bridge as `agent-peers hermes-bridge --hermes-profile <profile id>`; without that option, or with a profile id outside the scope grammar, the bridge claims no names.

The plugin sends one notification, an id-less line with no response: `delivery_result {session, message_id, accepted, reason?}`, reporting what the host did with a `peer_message`. `reason` is `queue-full` or `inbox-closed` when the plugin never offered it to the host.

`peer_message` notifications identify the private session, message ID, sender name, reply address (`from`), body and optional `in_reply_to`. Hermes creates no public registry entry. EOF and termination remove owned sockets. Standard output carries protocol data only; diagnostics go to standard error.

Messages use Claude's `<cross-session-message>` envelope. Incoming agent input is reframed as `<peer_message from="…" reply_to="…" id="…" in_reply_to="…">`, with a reminder that it carries no user approval. Codex and Hermes frames also say that it comes from another agent, not the user, that it should be answered with `send_peer`, and that only the brief can let a peer change the task ([steering a worker](compatibility.md#headless-codex-on-a-private-app-server)). Closing tags in message bodies are escaped. A frame is bounded to 1,000,000 bytes. Resource bounds, per-sender token buckets and duplicate-id suppression limit accidental floods; see the source constants for precise limits.

## opencode plugin and bridge

opencode **2.x** loads `agent-peers` as a server-side plugin. The plugin is deliberately thin: it registers `list_peers`, `send_peer`, `claim_name` and `release_name` immediately from `src/peer-tool-definitions.json`, forwards `instance`, `sessionID` and the arguments to a bridge, forwards `prompt`/`deleted`/`moved`/`closed` events, and executes only `host.session` and `host.synthetic`. Routing, names, delivery, receipts, dedup and pins are in the bridge (`src/opencode-bridge.mjs`), which the Rust port can replace behind the same protocol.

One bridge child runs per opencode server process and is shared by every location plugin instance in that process through a version-keyed `globalThis` handle. The child is a normal stdio process: its stdin is its lifecycle, so the last plugin instance closes it, and a killed server closes the pipe. There is no detached process or bridge socket. `bridge_command` is a plugin option (an array of executable and arguments); it is checked first and skips the Node lookup. Without it, the plugin resolves Node in this order: `AGENT_PEERS_NODE`, `node` on `PATH`, then the common version-manager and agent paths, newest first; each candidate is probed with `--version` and must be Node 22 or later. The result is cached for the server's lifetime; a failure is retried at most every 30 s. A configured `bridge_command` that fails is reported as `bridge-unavailable`, never silently replaced by Node.

**Identity.** Every tool call carries the caller's `sessionID`. The bridge reads `Session.Info` through the plugin, walks `parentID` to the root (at most 16 parents, cycles and missing parents are refused) and caches the child→root result. A child session gets no registry record or inbox of its own: it sends under its root's address and outbox, appears as `self.subagent: true` with the root's address/generation/claims and `threadId` = root session id, and gets `no-session` from `claim_name`/`release_name`. A root's automatic name is `opencode:<directory label>-<sha256(root session id)[:6]>`; a child's own `self.name` uses the child's directory/title and hash but its address is the root's. `OPENCODE_SESSION_ID` is not read by agent-peers: CLI identity remains Claude/Codex only.

**Registry record and inbox.** `$AGENT_PEERS_HOME/opencode-<rootSessionID>.json`, mode `0600`, carries `name`, `address`, `addresses`, `cwd`, `threadId` (the root session id), `pid` and `procStart` (the bridge child), `token` (one bridge instance), `generation` and `startedAt`. There are **no server fields**. `generation = sha256("opencode\0<rootSessionID>\0<bridge procStart>")[:16]`; the name owner is `sha256("opencode\0<rootSessionID>")[:16]`. The peer inbox is `join(socketDir(), "opencode-" + sha256(rootSessionID)[:16] + ".sock")`; the `<hash>` is the first 16 hex digits and includes no session text. The record is the exclusive bind seat: a missing path is created with `link`; an existing live record refuses with `inbox-unavailable`; only a predecessor confirmed dead is moved aside and replaced, after checking that its inode is still the one read; the record is re-read after publishing and the socket is created only then, with one more record check. A refused bind never creates an inbox or a name.

A bridge serves at most 64 roots. At the cap it evicts only the least recently active root that is idle (`Session.Info.time.idle` is present and `time.idle >= time.updated`) and holds no claimed names; eviction runs through that root's single-flight bind task, re-checks before closing, and leaves a busy root alone. With no idle unnamed candidate the new bind is refused `inbox-unavailable`. An evicted or deleted session reads `not-running` and rebinds on its next prompt or tool call. There is no automatic disk rebind.

**Delivery.** An inbound line is validated with the shared envelope reader, checked against the root's claimed names, admitted (dedup, per-sender bucket, queue bounds) and acknowledged with the shared receipts. The bridge then calls `host.session`: a staged `revert` drops `host-rejected` without touching it; otherwise the framed text is admitted with `host.synthetic({delivery: "steer", resume: true})`. Synthetic never commits a staged revert and is the only delivery path; there is no prompt fallback. A successful synthetic call gets `accepted`; a host not-found drops `inbox-closed` and unbinds; a lost or timed-out host call sends **no receipt**, because it may have landed. Late negative outcomes are appended with `host.synthetic({resume: false})`, batched; a failure there is logged and never retried.

**Protocol (internal, v1).** Newline-delimited JSON over the child's stdin/stdout, one message per line, at most 4 MiB per line. Every message carries `"v": 1`; plugin requests use `p-` ids and bridge requests `b-` ids. Plugin→bridge: `hello {instance, location}` → `{v, version, limits}` (once per instance), `tool {instance, name, sessionID, args}` → `{text, structuredContent, isError}`, and the id-less `event {instance, type: prompt|deleted|moved|closed}`. Bridge→plugin: `host.session {instance, sessionID}` and `host.synthetic {instance, sessionID, text, delivery, resume, description, metadata}`. There is no `bind`, `unbind`, `shutdown` or `host.notice`; closing stdin is the lifecycle. Error codes are `invalid-request`, `not-found`, `host-rejected`, `inbox-unavailable`, `bridge-closed`, `too-large`, `unknown-method` and `version-mismatch`; a host not-found is the caller's own session/instance and maps to `failed`/`no-session` for a tool, while a missing target peer remains the ordinary `send_peer` result. The protocol is not covered by semantic versioning; the plugin and bridge ship together.

**Two servers.** By default opencode's background service and a `--standalone` or `--server` process share one database. The first live bridge binds a root and owns its inbox and name; a second bridge sees the live record and refuses with `inbox-unavailable`. Running one session in two servers is unsupported: a `resume: true` delivery through the first server wakes its process-local runner while the other server may already be running the same session, which can start a second runner. Stop one server or do not run that session in both. `--standalone` sessions exist only while their CLI/TUI lives; a persistent peer needs the TUI or `serve --standalone` to stay up. `--auto` auto-approves permissions that are not explicitly denied, so peer input can lead to tool calls with no human approval step; do not use it with untrusted peers or sensitive repositories.

`opencode plugin add` installs its own agent-peers package, so the plugin and the global CLI can be different versions. `doctor` prints both and warns when they differ; pin one version. The plugin path never reads opencode's service registration or password.

## Troubleshooting

- **No Codex inbox:** it should open within seconds of the session starting. Run `agent-peers doctor`: the Codex app-server must answer. Check that the server is registered as `agent-peers` and that the session runs on the app-server agent-peers uses, not an embedded one (`codex exec`, `-c`, `--no-daemon`). A `list_peers` call in that session also opens it. Without a reachable thread, startup binding retries quickly, then every few minutes, and logs each failure reason once.
- **Wrong native target:** rediscover from the sending Codex session. A thread UUID alone does not establish native reachability.
- **Held Claude delivery:** review its inbound-message policy; agent-peers does not bypass it.
- **`not-running` for a listed peer:** the session exited, or a different process now owns its PID or inbox. Call `list_peers` and send to the session it shows.
- **`not-running` for a claimed name:** its holder stopped. The session that now has the role must claim the name (a Codex session and a Hermes conversation take back their own names automatically; a restarted Claude session runs `agent-peers claim` again). `not-found` means nobody claimed it.
- **`inbox-unavailable` for a running claimed name:** its holder runs, but under a Claude configuration or socket directory the sender does not use. Send from a session that shares the holder's `CLAUDE_CONFIG_DIR` and socket directory; nobody can take the name over while its holder runs.
- **`not-a-reply-target` from a claimed Hermes name:** a Claude sender must run `agent-peers resolve <name>` from its own session just before `SendMessage`, and use the address it prints. If `resolve` itself fails with `unknown-sender`, the Hermes bridge cannot see that Claude session; give both the same `CLAUDE_CONFIG_DIR`.
- **Hermes unsupported route:** use the documented host revision. Upstream `inject_message` is not an equivalent fallback.
- **Missing plugin dependencies:** run the exact install command in the plugin error, then reload through the host's supported lifecycle.
- **No opencode tools:** `agent-peers doctor` reports the binary, whether the global config lists `agent-peers`, and version skew. Install with `opencode plugin add agent-peers@next`, restart opencode, then call `list_peers` in the session. A session that has never prompted or called a tool is not yet reachable.
- **opencode `bridge-unavailable`:** the plugin could not start its bridge. Set `AGENT_PEERS_NODE` to a Node 22+ executable or the plugin option `bridge_command` to the bridge command; a configured command is never silently replaced by Node.
- **opencode `inbox-unavailable`:** another opencode server already serves that session (stop one), or all 64 roots are busy or hold names. Release a name or close an idle session; the session's next tool call reports the result.
- **Permission failure:** inspect directory ownership and modes. Do not make the socket directory globally writable.
- **Old reply address:** ask the peer to discover or send again after the original conversation closes; addresses are not durable mailboxes.

## Updating active integrations

Keep production launchers pointed at a tested installed snapshot, separate from development checkouts. Running Node processes cache their modules: changing a file does not update an existing sidecar.

Use the agent host's supported MCP refresh with the new snapshot's launcher. Codex can preserve conversations and active work while replacing an MCP connection; an already captured tool step may still use the previous connection. A live legacy inbox owner blocks unsafe takeover. Verify the new registry owner, all inbox paths, and a real reply before considering an update complete.

Missing Codex inboxes repair on the next tool call only while the sidecar still owns its registry token. An inbox owned by a replacement is never reclaimed. A Hermes bridge restart retires its private reply addresses, so the Hermes conversation must send again to establish a fresh return route; its claimed names are `not-running` until its next agent-peers call takes them back.
